# 工作流生产可用 V1

工作流从"可编辑、可运行"补全为具备**草稿发布、不可变版本、确定性执行、运行追踪和历史审计**的生产可用形态。本文面向使用者与集成方，说明版本模型、执行语义与运维约束。

## 1. 版本与发布模型

工作流定义升级为 `schema_version: 2`。草稿与发布版本是两套独立状态：

- `custom_agents` 保存**可编辑草稿**、单调递增的 `draft_revision`，以及指向当前生效版本的 `published_version`。
- `workflow_versions` 按（租户、智能体、版本号）保存**不可变**定义、配置快照、发布人与发布时间。

**保存草稿必须携带期望修订号**。服务端比对 `expected_revision` 与当前 `draft_revision`，不一致时返回 `409` 并带回当前修订号，禁止静默覆盖——编辑器可能长时间开着，两次保存之间他人可能已经改过定义。

发布流程先做结构、资源、表达式与可达性校验，再以事务方式创建新版本并推进 `published_version`。每次重新发布都生成更高版本，已发布版本不可修改或覆盖。

**旧数据迁移**：已存在的工作流在迁移时自动生成发布版本 1。迁移只做兼容性转换，不会用新增的严格校验阻断已经在跑的工作流。v1 定义中**存在多条出边的节点**显式迁移为 `all_match`，保持迁移前的行为；单出边节点为 `first_match`。

**只有已发布版本会被正式入口执行**。聊天、共享、IM、嵌入等入口都运行发布版本；复制和导入只生成未发布草稿。编辑器 Debug Run 是唯一的草稿执行入口，它会绑定发起时的草稿修订快照，不会改变当前发布版本，也不会影响正式入口。

## 2. 执行语义

### 每次运行绑定不可变快照

运行启动时绑定发布版本并保存定义快照。运行期间对草稿的编辑和后续发布**不会影响该次执行**，运行详情也始终用当次快照渲染——不会出现"看历史记录却加载了当前草稿"的情况。

### 分支模式

节点通过 `branch_mode` 决定出边如何选择：

| 模式 | 行为 |
| --- | --- |
| `first_match`（新建节点默认） | 按出边 `order` 稳定排序（同 `order` 按边 ID），取**第一条**命中条件的分支执行，后续出边不再求值 |
| `all_match`（旧多出边节点迁移结果） | **全部**命中条件的分支并行执行 |

没有命中任何条件边、也没有默认边可兜底时，返回明确的 `NO_MATCHING_BRANCH` 错误码，而不是静默结束。

### 节点与运行状态

节点状态统一为 `pending` / `running` / `succeeded` / `failed` / `canceled` / `skipped`；运行状态统一为 `running` / `succeeded` / `partial` / `failed` / `canceled`。

**失败可被条件引用**：节点失败后仍会写入变量表，因此 `nodes.<id>.status` 在失败分支里依然可读。命中失败处理分支的失败视为**已处理**，没有匹配分支的才是**未处理失败**。

状态归并规则：

| 条件 | 运行状态 |
| --- | --- |
| 所有活跃分支完成且无未处理失败 | `succeeded` |
| 成功终点与未处理失败并存 | `partial` |
| 没有成功终点且存在未处理失败 | `failed` |
| 收到取消信号 | `canceled` |

### 取消

取消以数据库中的 `cancel_requested_at` 为准。信号会传递到 HTTP、LLM、MCP、Skill 等实际执行上下文；运行中节点尽力停止并标记 `canceled`，尚未认领的待办会被删除并归档为取消，不留残余任务。取消接口是幂等的，重复调用不会重复写入终态事件。

### 持久化、恢复与重试

数据库中的 `task_pending_ops`、分支变量检查点和节点 attempt 是执行状态的唯一事实来源，Asynq/Lite 任务只负责唤醒 worker。每个唤醒最多认领并执行一个节点；节点完成、变量检查点、下一批待办和生命周期事件在同一事务中提交。重复投递会识别已完成 attempt 并直接返回。

服务启动时会扫描仍为 `running` 且存在 durable 待办的运行，重新创建唤醒任务，因此入队失败、worker 崩溃和进程重启不会丢失运行。自动重试仅覆盖超时、限流、网络错误和上游 5xx；配置、权限和不安全副作用不会自动重试。HTTP 的 `POST`/`PATCH` 等副作用方法必须配置幂等键模板；MCP/Skill 只有声明安全重试才允许自动重试。

整次重跑使用原运行的定义、配置和输入快照；失败节点重试从对应分支的变量检查点继续，并生成新的运行记录和 attempt 关联。正式运行和 Debug Run 都至少一次投递，不宣称通用 exactly-once。

### 答案输出

节点产生的用户可见内容**先缓冲**。调度结束后按分支路径和出边顺序**确定性聚合**，多段内容以空行连接，**只发送一次**最终答案。

- `succeeded` / `partial`：发送结果。`partial` 附带结构化的部分失败状态。
- `failed` / `canceled`：**不发送**缓冲答案——避免先展示结果再宣布失败。

## 3. 运行记录与保留

`workflow_runs` 记录租户、智能体、发布版本、定义快照、触发来源、会话/消息关联、状态、耗时、usage、摘要与错误；`workflow_run_nodes` 记录节点、分支路径、状态、起止时间、耗时、usage、输入输出摘要与错误。

**权限**：Viewer 可查看发布定义、脱敏运行摘要和生命周期事件；智能体所有者或 Admin 才能保存、试跑、发布、恢复版本、查看完整节点载荷、取消和重试。所有查询和写入强制限制在当前租户。

**脱敏与截断**：输入、输出、HTTP headers、工具参数和错误在持久化前统一脱敏；每个摘要字段最多保存 8 KiB 并记录 `truncated` 标志；不保存密钥或认证信息。

**保留**：正式运行默认保留 90 天，Debug Run 默认保留 14 天；两个期限都可通过环境变量配置，由后台 runner 分批清理运行、节点、分支和事件。发布版本在智能体存续期间持续保留（删除智能体时随外键级联回收）。

## 4. 生命周期事件

专用事件类型：

- `workflow_run.started` / `workflow_run.completed`
- `workflow_node.started` / `workflow_node.completed` / `workflow_node.failed` / `workflow_node.canceled`

事件统一携带 `event_id`、`sequence`（单次运行内单调递增）、`run_id`、`workflow_version`、`node_id`、`branch_path`、`status`、时间与脱敏摘要。

前端按 `run_id + sequence` 去重和排序，并以集合维护多个活跃节点——**不再**从 `workflow.<nodeID>` 工具名推断执行状态。旧的合成 tool call 事件仍然保留，作为旧客户端的兼容数据，但不再是轨迹状态的权威来源。

## 5. 导出与导入

导出格式带独立的导出格式版本和工作流 `schema_version`，**不包含**密钥、运行历史或环境绑定值。

导入流程：旧版本迁移 → schema 校验 → **资源映射预览**。缺失或有歧义的资源必须由用户选定，禁止静默降级。导入结果只生成未发布草稿。

## 6. 明确边界

V1 不实现：多入边汇聚、循环、子工作流、人工审批、调度触发和 Webhook 触发。

V1 提供编辑器内 Debug Run，但它不是正式运行：Debug Run 只绑定草稿快照，正式入口始终只使用已发布版本。旧版本的“恢复”只复制为新的草稿修订，之后仍需重新发布。

**迁移与部署**：迁移 PostgreSQL `000097_workflow_production_v1`（SQLite `000018_workflow_production_v1`），默认随应用启动自动执行；若关闭 `AUTO_MIGRATE`，须先执行迁移再启动新版本。存量工作流会在此迁移中回填发布版本 1。
